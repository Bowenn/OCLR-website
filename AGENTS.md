## Contributor setup and workflow

- Before coding, read the Issue's latest comments and claim it with `xxx 正在开发中`, identifying the developer/agent session and branch. Re-read after posting; the earliest active claim takes priority if claims race. If someone already owns the work, coordinate before starting duplicate work. No claim comment ("空 comment") means unclaimed; do not post blank comments or treat unrelated comments or silence as a release.
- When stopping work, the owner posts `xxx 终止开发` with progress and handoff notes. Do not release another contributor's claim without their agreement. When implementation is ready, link the commit/PR and state that it awaits review; keep ownership through review unless explicitly handed off or terminated. Issue closure remains subject to maintainer acceptance below.
- Start with [README](README.md) ([简体中文](README.zh-Hans.md), [繁體中文](README.zh-Hant.md)), [development](docs/development.md), the requested GitHub issue and relevant [module documentation](docs/README.md). Use Node.js 24 LTS (minimum 22.13), npm and the existing lockfile. Run `npm ci`; do not introduce a second package manager.

This uses the dedicated loopback-only `oclr_frontend_test` database and clearly synthetic editions. Keep existing local configuration intact. Do not run automated destructive fixtures against this preview database; use a separate isolated test database. See the development guide for an existing PostgreSQL setup.
- No organizer credentials or private production data are needed for the synthetic UI preview. Real OAuth login and role-specific workflows require separately approved configuration and grants; there is no development authentication bypass. Do not copy real registrations, private answers, tokens, uploads or dumps into fixtures or seeds.
- For direct remote reads, follow [Developer API access](docs/developer-api.md) and the [saved-data contract](docs/read-api.md). Access requires an explicit Developer grant where applicable; Admin or repository collaborator status does not imply one. Tokens are short-lived, scoped, read-only and revocable, and must not enter source, URLs, logs, screenshots or `NEXT_PUBLIC_*`. The generated [OpenAPI](docs/read-api.openapi.json) is also served at `/api/v1/openapi.json`; the full saved-read remote frontend setup and explicit authorization/transport limits are documented in [remote development](docs/remote-development.md).
- **External contributors:** use a fork when needed and a focused branch (prefer `codex/` for agent-created branches) based on current upstream main. Check which remote is your fork and which is the canonical repository; fetch the canonical main before editing. Push only to your own fork/authorized feature branch when requested, and submit a PR for maintainer review when requested. Do not push directly to canonical main, merge, close issues or update another person's checkout. If publishing was not requested, leave the patch/commit ready for review and report it.
- **Maintainer-authorized sessions in the organizer checkout:** commit each requested issue separately and push automatically within the authorized scope; verify the remote SHA and update the issue. Do not open a PR unless requested. Fetch origin before editing and fast-forward the working branch to latest main when safe. After a completed push to main, also fast-forward the user's main checkout and verify it matches origin/main. A feature-branch push does not authorize merging it into main; an isolated worktree does not replace synchronizing the organizer checkout after an authorized main update.
- **Everyone:** preserve unrelated edits, local environment files and other contributors' work. Never force-push, bypass branch protection, reset/overwrite changes or rewrite a shared branch. If a safe fast-forward is blocked, leave the changes intact and report the blocker. An inaccessible issue or CI check is a limitation to report, not permission to invent its contents or status.
- Keep changes focused on the requested scope and explain behavior, relevant issue, verification and remaining limits in the handoff/PR. Maintainers close issues only after acceptance is verified; contributors report evidence and leave closure/release decisions to maintainers.

A contribution or PR does not authorize deployment, service restarts, production migrations, role grants or access to runtime secrets. These constraints guide changes to operational code; run live operations only when explicitly requested.

- Deployment target: **Rocky Linux 10**, with systemd, **existing separate PostgreSQL** and **existing separate Nginx**. Do not install or initialize replacement database/proxy services. Follow the Rocky-specific section in docs/deployment.md; never disable SELinux or expose the Node listener unnecessarily.
- Organizer-selected internal PostgreSQL connections may explicitly use `sslmode=disable`; retain password authentication, source-IP restrictions and separate runtime/migration roles. Do not reintroduce mandatory DB TLS or infer this choice for public HTTPS, which remains required.
- Production entry point is Bash (`scripts/production.sh`), with npm aliases. Preserve explicit exported-environment configuration, migration-secret isolation, fail-closed setup and direct Node exec for systemd signals.
- Simple Rocky operator entry point: `sudo bash scripts/oclr.sh deploy|update`, then `sudo oclr update`. Root only provisions packages/accounts/service rights; runtime.env loading, builds and the shared backup/migration engine run as oclr. Keep root-owned bootstrap/unit definitions independent of app-owned checkout content. Migration prompts accept normal passwords and escape internally; never persist them or pass them in argv.
- Production preparation: `npm run production:setup -- --dry-run`, then setup only on the intended host after approved environment configuration and backup. `npm run production:start` serves a prebuilt release without migration. See README and docs/deployment.md. Do not claim real deployment/live OAuth or organizer rehearsal passed unless performed. No assumed domain or credentials.
- Routine updates use `scripts/update.sh --ref FULL_REVIEWED_COMMIT_SHA --apply` from a clean operator checkout, with single-host locking, a new release directory, verified backup, migration history/target checks, systemd switching and exact-release local/public health. Preserve its fail-closed recovery and secret isolation. Never build over the serving release or automatically restore/down-migrate a live DB.
