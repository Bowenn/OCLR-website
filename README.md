# OCLR — osu! Chinese League Rookie

Official community tournament website. OCLR is not affiliated with or endorsed by osu!.

## Local development

Use Node.js 24 LTS (minimum 22.13) and npm. Run `npm ci`. For database-backed features, copy `.env.example` to `.env.local`, configure `DATABASE_URL`, and run `npm run db:migrate` before starting the app. Run `npm run dev` and open http://localhost:3000. Never commit secrets.

One Next.js App Router application uses strict TypeScript, React and Tailwind CSS. Shared tokens and responsive patterns live in `src/app/globals.css`. Static tournament information works without external services; authentication, registration, teams and live draft data require PostgreSQL. Empty production content stays unpublished until approved by organizers.

## Checks and hosting

`npm run check` runs ESLint, generated route types and TypeScript. `npm run build` creates the production build; `npm start` serves it on a conventional Node.js host. CI runs the same checks. No Vercel services are required.

## Design and content

The committed `docs/design/oclr-website-concept.webp` is a visual reference only. Its dates, statistics, format, identities and expanded tournament name are placeholders. The correct name is **osu! Chinese League Rookie**. Registration is individual; teams are formed through the staff-appointed captain draft.

## Tournament content

Tournament editions live in PostgreSQL and are managed through `/admin/tournaments`. Global Admins create private editions; edition-scoped Admins configure their assigned tournaments. Creation needs only a name: the URL slug is suggested and editable before creation; UTC is the neutral initial zone. Drafts may have no summary, season or artwork. Add public copy before publishing. Save general information, rules/eligibility, registration and milestones independently, then deliberately publish. The slug is immutable. S11 starts unpublished with its existing artwork and no invented dates, rules or registration window.

Publishing never enables registration. Rules, eligibility and milestones are optional, independent content. Registration requires publication, privacy configuration, explicit enablement and a valid unlocked window. Advance enabling is supported; submissions are accepted from opening (inclusive) until closing (exclusive). Only configured Rules/Eligibility are acknowledged. Missing rules use a null version and absent eligibility uses a null acknowledgment; no synthetic consent is generated. Existing draft/team locks still protect competition setup. Changed rules cannot reuse a version for different text. Configuration snapshots preserve earlier rules, questions and answers without requiring a retention-approval checkbox or coupling question edits to rules versions.

Registration dates, withdrawal deadlines, milestones and fixture times use separate Date and 24-hour `HH:mm` fields with the configured IANA zone immediately after the time (and a date-specific offset when available). Partial edits and daylight-saving gaps block saving; duplicated hours require an explicit UTC offset. Optional dates can be cleared to TBA. Unchanged timestamps retain their original seconds and offset; editing the date/time sets seconds to zero. Changing a fixture’s time zone keeps its scheduled instant and updates the local display. General settings and Fixtures share a searchable city/IANA selector; UTC is the default, valid saved aliases are retained, and supported zones have a bundled fallback list.

`OCLR_EDITIONS_FILE` is no longer read by the application. `drizzle/legacy-editions.json` is an archival migration fixture, not runtime content. Use the one-time, conflict-protected import only when upgrading an installation with externally mounted JSON; see [migration and rollback](docs/deployment.md#tournament-configuration-cutover). Normal tournament management requires no JSON edits or redeployment.

`npm test` runs configuration/business tests. `npm run test:e2e` runs Playwright against the production build (install Chromium using `npx playwright install chromium`; set `PLAYWRIGHT_CHANNEL=chrome` to use installed Chrome). Test data must never be copied into production configuration.

The development dependency audit reports an esbuild development-server advisory through Drizzle Kit’s legacy loader and an upstream, unpatched `braces` stack-exhaustion advisory through Next.js lint tooling. No esbuild server or Drizzle Studio is exposed, and lint patterns are repository-controlled. `npm audit --omit=dev` is clean; review upstream patches regularly without downgrading the application or forcing unrelated dependency changes.

## osu! authentication and PostgreSQL

Set `APP_URL`, `DATABASE_URL`, `OSU_CLIENT_ID`, `OSU_CLIENT_SECRET`, `PRIVACY_CONTACT_OSU_ID` and an organizer-approved `PRIVACY_RETENTION_NOTICE`. Register **exactly** `APP_URL/auth/osu/callback` as the osu! callback, with no extra trailing slash. Follow the [official osu! OAuth documentation](https://osu.ppy.sh/docs/index.html#authentication). Only `identify` is requested. Designate one verified Admin using a positive numeric osu! ID in private `.env.local`; do not copy the bootstrap allowlist. Existing sessions and identities remain intact, but new sign-in and registration fail closed until the new contact variable and retention notice are configured. See [privacy contact setup](docs/deployment.md#privacy-contact-setup) when upgrading from the email setting. Neither OAuth access nor refresh tokens are stored; identity is refreshed on login. No password accounts or production test-auth route exist.

Run `npm run db:migrate` after pulling database changes and before starting the updated app. The Drizzle configuration uses Next.js environment loading, including `.env.local`; an explicitly exported `DATABASE_URL` takes precedence. CLI commands default to development environment files; set `NODE_ENV=production` when using production files. Migration `0017` adds `staff_roles.about_published`; missing it causes Staff Management queries to fail. Existing staff stay private after migration. Generate reviewed SQL changes with `npm run db:generate`, commit the migration and snapshots, then apply migrations before deploying application code. Use separate databases and OAuth apps for staging/production, verified TLS for remote PostgreSQL and HTTPS on the canonical origin. Session cookies are HTTP-only, SameSite=Lax, host-only, and Secure with `__Host-` names on HTTPS. Raw 256-bit session tokens never enter the database; only SHA-256 hashes do. Sessions expire after seven days; logout revokes the current session. OAuth state is one-use, browser-bound and expires after ten minutes. Reverse proxies must redact callback query strings and never log Authorization or Cookie headers.

Database-backed tests require **an isolated database whose name contains `test`**, passed explicitly as `TEST_DATABASE_URL`. Apply migrations there first, then run `TEST_DATABASE_URL=... npm test`. Migration-upgrade tests create and drop isolated temporary databases, so the test role needs `CREATEDB`; never use a production/runtime role. Provider HTTP responses are mocked only inside test files; callbacks, state consumption and sessions use real PostgreSQL. Live osu! consent/token exchange requires organizer-owned credentials and remains unverified until staging login/logout with two real accounts is performed.

## Registration lifecycle

Applications are **individual**, with one database-enforced record per stable osu! identity and edition (including withdrawn/rejected records). No automatic resubmission is provided. Only edition-approved text questions are collected. Configured eligibility is disclosed and acknowledged; staff assess the approved rules manually, never inferred rank/country/age restrictions or claims of official osu! validation. Unknown fields, forged identities, missing applicable acknowledgments and stale rule versions are rejected. Repeated/concurrent submissions cannot create duplicates.

`pending` means awaiting staff review; staff may change it to `accepted` or `rejected`. A player may withdraw a `pending` or `accepted` application only before the explicitly configured `withdrawUntil` and while the edition is unlocked. `withdrawn` is terminal; rejection cannot be changed by a player. No withdrawal deadline means no self-service withdrawal. Captain appointment/locked draft state prevents self-service withdrawal and requires staff review. Every transition is recorded with actor and time; review is separate from captain/team assignment. Edition-scoped transaction locks serialize eligibility-affecting changes and draft lock against withdrawals/submissions.

## Staff provisioning and reviews

There are no seeded administrators. Verify the first administrator's numeric osu! profile ID out of band, explicitly place that ID in the server-only `ADMIN_OSU_IDS` comma-separated bootstrap allowlist, deploy/restart, and authenticate normally. Legacy `STAFF_OSU_IDS` is ignored: review each old operator's responsibilities before explicitly granting a role. Never copy the old list automatically.

Administrators manage persistent Admin, Mappooler and Referee assignments at `/admin/staff`. Recipients must first authenticate through osu!. Grants may be global or limited to a configured edition; multiple grants combine capabilities. An edition administrator can only grant/revoke roles within that edition. Every confirmed grant/revocation automatically records actor, recipient, scope and before/after assignment. Revocation applies on the next server check, including existing sessions. Captains receive no staff privileges from their appointment.

Keep bootstrap access restricted for recovery. An environment bootstrap administrator cannot be revoked through the website: remove the ID from `ADMIN_OSU_IDS` and restart. Before removing the final bootstrap ID, verify a persistent global Admin can sign in. A scoped Admin cannot recover global access. Never grant roles from usernames, client cookies or request-supplied actor identities.

Staff enter `/admin` for a role-aware overview, then select a tournament at `/admin/tournaments`. The selected workspace has grouped operational navigation, a tournament switcher and breadcrumbs. General/rules/registration/milestone/publication settings live under `/admin/tournaments/[edition]/settings`; registration review lives under `/admin/tournaments/[edition]/registrations`, with `/admin/registrations` for authorized cross-edition search. Legacy filtered `/admin` bookmarks and registration detail URLs redirect safely. Global Staff Management and Audit stay outside tournament navigation; personal accounts remain on the public website. All page queries, APIs, reviews and exports also enforce authorization on the server. Pending applications may be accepted/rejected with explicit confirmation; rejection requires a player-visible explanation. Reviews use transaction locks and a version check, so stale or concurrent decisions are rejected. Locked editions cannot be reviewed. Audit events include actor, before/after status, timestamp and reason. CSV exports contain only ID, username, edition, status and submitted time; formulas/control-prefixed cells are neutralized and quotes escaped. Approved question answers and internal audit data are excluded from CSV. Exports are limited to 10,000 filtered rows and should be handled as private staff data.

## Captains and eligible pool

The captain workspace shows eligible players and appointed captains as avatar/country cards. Drag an eligible player into the captain area or use its Appoint button. Reorder captains with the grip (mouse/touch) or labeled move buttons, then Save captain order. Publication, replacement, revocation, availability and locking remain under advanced controls. Country details use existing cached official profiles; only visible missing identities are lazily requested through the existing protected profile endpoint, serially, with unavailable data labeled honestly. Team setup links guide organizers from accepted applications to captains and team configuration instead of leaving an empty page.

Staff use `/admin/tournaments/[edition]/captains` to appoint/revoke/replace accepted, available individual players, save a complete captain order, mark a noncaptain unavailable with a reason, and lock reviewed setup. There are no assumed captain counts, roster sizes, clocks or snake rounds. Commands validate the current setup revision; routine saves do not require a written reason or extra dialog, while publication and consequential changes require confirmation; edition locks and database uniqueness protect concurrent actions. Captains cannot withdraw themselves or gain staff powers. Captain/pool identities remain private until an explicit staff publication approval. Locked setup rejects normal changes; supervised recovery must be handled through the draft controls rather than silent edits.

## Teams

Staff configure exactly one approved team identity per captain at `/admin/tournaments/[edition]/teams` **before locking setup**. Optional capacity is a maximum including the captain, not an invented required roster size. Captain membership is created transactionally. A partial unique PostgreSQL index enforces one active membership per player per edition; composite foreign keys prevent cross-edition assignments. Revoking an unstarted captain archives their team and ends membership without erasing history. Assigned draft rosters require supervised correction.

Captains view only their own team at `/tournaments/[edition]/team`; no self-service team creation, invitations, roster edits or unapproved branding edits exist. Public `/teams` routes project approved identities only. Rosters require finalization by the draft engine and separate staff publication. Private memberships, capacity, internal operations and unpublished identities are excluded. The bracket consumes these finalized, published team IDs directly.

## Authoritative draft engine

Both the active captain and authorized staff use **the same** `pickPlayer` command and `/api/tournaments/[edition]/draft/picks` endpoint. A request contains only session ID, expected revision, turn index, candidate ID and idempotency key. Actor, action mode and receiving captain/team are derived on the server. One transaction locks edition/session, validates the frozen pool and current turn/capacity, inserts the uniquely constrained pick and membership, advances the turn/revision and records the actual actor/mode in the private audit. Captain status never grants staff control.

Staff configure the **full team-ID turn sequence** after reviewed captain/team setup is locked. Choose Snake (alternating captain order), Repeat forward, or Custom, set the pick-round count, and inspect the numbered preview before saving. No mode, roster size or clock is assumed; ambiguous saved sequences display as Custom. Save validates the draft and reviewed setup revisions, eligible player count and configured capacities (including captains). `ready` confirms and freezes the saved order and accepted available player pool, revalidating current constraints. States: setup → ready → live ↔ paused → completed → finalized; staff can abort only from setup/ready/paused/completed, then confirm recovery to unlocked setup. Every control checks the expected revision; routine saves/pause/resume are direct, while freeze, publication and consequential actions require confirmation.

Staff explicitly start/release an approved public draft. Confirmed picks and normal transitions then update public/captain snapshots atomically with the mutation; public snapshots exclude actor IDs, action modes, private answers, audit reasons and idempotency keys. Remaining pool identities require separate approval. Captain snapshots contain only the published board plus approved eligible identities needed for selection. Picks require a released board, but no separate per-turn publication. Public reads never advance a draft. Duplicate retries by the same actor/key return the existing receipt; different payloads with the same key fail.

All appointed captains use `/tournaments/[edition]/draft/captain` to browse the last published eligible pool and their own roster. The active captain can drag a player into My Team or choose a card by click, keyboard or touch, then confirm the pending pick once. Dragging never writes a pick or moves a roster member. Waiting captains have a searchable read-only board. Staff use the same picker for the active captain. The UI clears unconfirmed selections when disconnected or when the published revision changes; sent requests retain their idempotency key for safe receipt retries after uncertain network failures. Rosters update only from authoritative snapshots, with no optimistic captain roster publication.

Supervised corrections are deliberately limited: pause (or complete), confirm voiding the last pick, preserve its history, end its membership, automatically update the corrected snapshot, then resume. Earlier corrections require undoing subsequent picks in reverse order, or explicit abort/recovery; finalized drafts are immutable. Abort voids draft picks/memberships and preserves audit/history. Finalization requires all configured turns committed, roster invariants satisfied and last picks published, then marks teams finalized. Team roster publication remains a separate explicit staff approval. Unconfirmed substitutions/post-finalization corrections are not invented.

## Read-only brackets and results

Once an edition has database fixtures, its database competition pipeline is the sole score authority. `/tournaments/[edition]/bracket` adapts published knockout fixtures and approved published result revisions into the existing responsive bracket renderer, with a keyboard-accessible full match list and source-detail links. Progression uses only explicitly configured winner/loser fixture relationships. No elimination format, bye, forfeit or winner is invented.

Legacy `src/content/brackets.json` or `OCLR_BRACKETS_FILE` remains a read-only compatibility source **only for editions with no database fixtures**. Once any database fixture exists, legacy scores are ignored for the entire edition, including when all database fixtures are unpublished. Never add independent file-based scores to an edition managed through referee review. Existing synthetic legacy fixtures continue to test the renderer.

A hidden or unresolved parent result yields a TBA slot, never the future fixture's stored team assignment. Publishing a corrected parent winner immediately withholds a downstream score/MP source when its approved teams no longer agree with progression. Staff must review affected fixtures, withdraw an invalid result, explicitly amend the unpublished fixture if needed, and follow fresh import/review/approval/publication. Historical revisions are retained. The same database projection drives schedule, result pages, standings and bracket so corrections cannot leave contradictory public scores.

## Competition mappools

Published maps appear directly at `/tournaments/[edition]/mappools`, grouped by stage and collapsible rounds. When both stages have released pools, keyboard-accessible tabs switch the visible stage in place. The first round opens automatically; each pool retains its shareable detail URL. Desktop rows group stats alongside covers, difficulty and mapper credits; phone layouts expose additional stats through Details. Base SR remains separate from saved provider-calculated Mod SR; NM uses Base SR, and unknown FM/TB mods remain variable.

Admin and Mappooler assignments grant access to `/admin/tournaments/[edition]/mappools`. Create independently named/ordered rounds under Group Stage or Knockout Stage, then draft pools. NM/HD/DT/HR/FM/TB slots have database-unique category/index positions. FM is disabled unless explicitly configured as Free Mod or Force Mod; enter only approved restrictions. Changing category/index, replacing/removing a map, reordering, refreshing metadata and publishing are automatically audited and require the current pool version. Routine saves apply directly; publication and removal retain explicit confirmation. Conflicting edits return 409 and refresh the editor.

Paste a numeric beatmap ID or canonical osu! difficulty URL to preview the cover, artist/title, difficulty, mapper, base stars, BPM and duration before saving. Song metadata is read-only. The protected same-origin `/api/admin/tournaments/[edition]/mappools/preview` endpoint requires edition-scoped Admin/Mappooler access. Input changes cancel old requests; collapsed map editors perform no lookup. Mod categories remain tournament slot labels, and the displayed base rating is not a mod-adjusted calculation. Bulk import keeps verified base metadata; it does not infer a mod combination from a slot category. Request official adjusted attributes explicitly while editing a draft pool. Public reads never calculate, backfill or modify published maps.

Bulk import accepts 1–50 plain BIDs, canonical `/beatmaps/BID` URLs or `/beatmapsets/SET#osu/BID` difficulty URLs. Select the category once; plain rows append after its highest saved slot, leaving existing gaps untouched. Advanced `NM1 4184799` / `HD1 URL` rows can be mixed in; explicit positions are reserved before automatic assignment. Set-only URLs cannot identify a difficulty. Preview reports resolved slots, malformed input, duplicates and saved-slot conflicts; reuse across different categories is flagged for organizer review. The official [batch endpoint](https://osu.ppy.sh/docs/#get-beatmaps) deduplicates IDs and shares the same bounded snapshot cache. Save recomputes slots from the original text on the server, revalidates fingerprints and commits the complete batch, pool version and audit together. Stale imports keep pasted text for another preview. In Maps, drag handles work with mouse/touch; keyboard arrows/Home/End, up/down buttons and a position picker provide alternatives. Moves stay local until **Save order**; that single mutation normalizes only the selected category. Batch edit can explicitly insert selected maps into an occupied destination, shifting/renumbering that category; choose an insertion position within the resulting list. Removal remains confirmed and metadata refresh is all-or-nothing. Completed-fixture locks and stale revisions remain protected; valid edits to unlocked public pools remain public.

Select calculation mods explicitly when adding/editing a slot. The official [Beatmap Attributes endpoint](https://osu.ppy.sh/docs/#get-beatmap-attributes) supplies calculated SR, available max combo and supported ruleset attributes. Combinations use standard mod settings, with no custom speed assumptions. Base AR/OD/CS/HP, stars, BPM and duration remain separate; FM/TB default to variable/unconfigured. Saved calculation configuration survives metadata refresh; any failed base/attribute lookup leaves all selected entries unchanged. Attribute snapshots are bounded to 200 cached combinations with a 15-minute expiration, keyed by map/ruleset/mods and base fingerprint. No database migration is needed for optional fields in the existing metadata JSONB; older entries remain base-only until refreshed. A configured round mode is enforced; absent round rules do not invent a mode restriction.

Preview and Save share the existing server-side [official osu! API](https://osu.ppy.sh/docs/#get-beatmap) client-credentials `public` token and verified cache. Tokens never reach browser clients. Every Save validates the map server-side; a changed preview fingerprint returns 409 and requires a refreshed preview. The actual provider fetch time is persisted. Public reads use saved metadata without calling osu!. Provider failures/deletions preserve entries, versions and audits. The process bounds its cache to 200 records, successful snapshots to one minute, concurrent distinct lookups to six, and failure cooldowns to 10 seconds (60 seconds for missing/rate-limited maps). Shared provider pacing, queues, timeouts and retries still apply. When scaling Node processes, keep aggregate traffic within official application limits.

Browser tests launch a guarded, test-only transport fixture through `tests/fixtures/osu-provider.ts`; it requires an isolated test database and the loopback browser server, and supplies synthetic public beatmap responses only. Application code has no provider-mocking switch or authentication bypass. A live server-side client-credentials request on 2026-10-20 also successfully retrieved official beatmap 75. A read-only live check on 2026-10-20 additionally retrieved BID 4184799 using the official batch endpoint and its DT attributes. No tournament records were created. These checks verify metadata/attribute transport, not full user OAuth consent or deployment.

Only released pools are returned by public pages/APIs, including direct UUID requests. Unlocked public pools can be edited directly; full revisions remain in private audit history. A completed-fixture lock permanently prevents map/settings/round-label changes, even after unpublishing. Create a new pool rather than rewriting historical competition maps; the results service sets this lock atomically when a fixture is approved. Locked pools reject ordinary publication/content changes; create a replacement pool for new competition content.

## osu! player profile snapshots

Published directory and team entries link to `/players/[osuId]`; `?edition=<slug>` preserves tournament context and `mode=osu|taiko|fruits|mania` selects an explicitly labeled ruleset. Directory reads and Next.js link prefetching never fetch provider profiles. Profile pages and `/api/players/[osuId]` check published participation before looking up metadata and again after provider I/O. A cached profile does not make a private applicant public. Anonymous refresh parameters are rejected.

`getOsuUserProfile(id, mode)` reuses the [official user endpoint](https://osu.ppy.sh/docs/#get-user) through the existing application `public` token. The fixed path includes `key=id` to prevent legacy numeric-username fallback; returned IDs are verified. No new player OAuth scopes or retained provider tokens are required. Only a compact validated public projection is stored in `user_profile_cache`, independently of participation and OAuth identity. Optional unavailable/invalid fields become null; unsafe numeric scores are omitted rather than rounded, while exact score strings retain precision. Provider contact fields and account history are discarded. Successful lookup updates only an existing user's mutable username, preserving all stable references.

Snapshots expire after **30 minutes** and are labeled with their source, ruleset and last successful update. The PostgreSQL cache holds at most **1,000 ID/ruleset keys**, evicting oldest attempts. In-process coalescing and database refresh claims deduplicate requests across instances; late claims cannot overwrite newer work. Refresh attempts are spaced by at least one minute per key, with five-minute backoff after failure. Temporary failures retain the last good snapshot with a stale notice; closed/deleted profiles are unavailable while their previous snapshot remains stored. Per-process provider pacing/queue limits still apply; account for aggregate traffic when scaling processes.

Profile lookup is API-only: the protected `POST /api/admin/profiles` supplies in-context Captain identity enrichment and throttled refresh for Admins with registration permissions. There is no standalone Profile or Beatmap lookup page; beatmap previews and bulk lookup stay in the Mappool workflow. Mappoolers, Referees, captains and ordinary accounts have no lookup privilege through those roles. Lookup never creates a user, publishes participation, changes eligibility or approves a registration. Use the organizer regression input `https://osu.ppy.sh/users/651307/osu` after configuring real API credentials. Automated fixtures are synthetic; the unauthenticated official request returned HTTP 403, so that player's current statistics remain unverified.

## Competition fixtures and result foundation

Admin manages `/admin/tournaments/[edition]/matches`; Referee assignments expose only that operator's fixtures. Both teams must have finalized, published identities/rosters. Fixtures reference existing edition/round/team IDs and an optional pool from the same round. Enter confirmed match times in the displayed IANA zone, or leave time TBA. Match options contains optional pool, order, status and progression settings; new fixture positions follow the selected round’s existing matches. Routine changes require the current version and are audited automatically; safe label/time edits retain publication, while active proposals and approved structural history protect teams, rounds, pools and progression. Winner/loser links are optional, explicitly configured knockout relationships; cycles and cross-edition/stage references are rejected. No automatic forfeits or advancement rules are assumed.

Round scoring remains `null` until explicitly configured: rules version, game mode, supported team/scoring mode, score aggregation, players per game, first-to/fixed-map series and substitution policy. ## Multiplayer source parsing

The single server API client uses the official [Get Match endpoint](https://osu.ppy.sh/docs/#get-match), `public` client-credentials scope and response version `20220705`. The independent history fetcher requests ascending `after` pages (100 events), deduplicates events/games, checks reported boundaries and detects history/game changes during retrieval. Imports are bounded to 100 pages, 10,000 events, 3,000 games and 8 MiB of aggregate provider responses; reaching an incomplete range cannot produce a final result. It retains validated scoring/event provenance and omits unrelated provider user profiles. A SHA-256 fingerprint excludes retrieval time so identical source facts remain idempotent; refresh comparisons identify added, removed and changed games.

The side-effect-free scorer attributes players using the fixture's official team IDs and rosters, never lobby-title names. Incomplete, conflicting, mixed-team or unsupported scores cannot silently produce winners. ## Referee review and result approval

An assigned Referee or Admin opens `/admin/tournaments/[edition]/matches/[fixtureId]`, imports a canonical osu! MP link using the server-side client-credentials configuration, and reviews every game. Include/exclude decisions, exclusion/override reasons, explicitly permitted substitutions and mod compliance are validated again on the server. The UI displays the current scoring policy and derived series; no client-supplied winner or score is accepted. Internal reasons and individual provider scores stay staff-only. The separate public result note is intended for publication.

Every import is fingerprinted and immutable. Identical imports reuse stored games; retries use actor-scoped request keys. Changed source histories show added, removed and changed games and require new review. Competing submissions with the same expected version produce one committed result and a 409 conflict. Reload and server restart read authoritative database state. Provider failures preserve prior sources and results.

Submitting creates a numbered immutable revision containing source, roster, pool and scoring-rule evidence, plus per-game attribution confidence and player/team evidence. Only Admin can approve, reject, withdraw or publish. The normal final action is **Approve & publish result**, after reviewing dependencies; older approved-only revisions can still be explicitly published. Approval reserves the included game IDs within the edition and permanently freezes the associated mappool. Publication requires both explicit Admin approval and a published fixture; imports or referee submissions never publish automatically. A correction follows the same review/approval/publication sequence. The old published revision remains authoritative until its replacement is explicitly published. Unpublishing withholds the public result; withdrawal also releases game claims, preserving all source/revision/audit history and inventing no forfeit. Active reports must be withdrawn before changing fixture identity; fixtures with approved history require a replacement for structural changes, preserving historical snapshots; scoring corrections receive a new policy release automatically and never rewrite saved approved snapshots. Unchanged scoring, standings and group-assignment saves retain their existing policy identifiers. Ordinary views show workflow states; technical identifiers remain in protected audit/provenance details. Published tournament Rules identifiers remain explicit because players acknowledge those releases.

Automated validation uses synthetic official-shaped API responses, real PostgreSQL transactions and isolated desktop/mobile browser sessions. Browser tests seed stored synthetic snapshots directly into the test database; there is no production mock provider or authentication bypass. ## Public competition center and group standings

Anonymous visitors can browse edition Players, Mappools, Schedule, Results, Bracket, participant/team pages and `/tournaments/[edition]/matches/[fixtureId]`. Edition navigation exposes these destinations even before publication, with meaningful empty states. The results list filters stage, round and publication status; scheduled fixtures can exist without scores. Public match details show approved team totals, included beatmaps/mods, a released-mappool link, an explicit public note, MP source and publication time. Private imports, player-level provider scores, review reasons, actor IDs and substitutions are never part of public result DTOs.

Public GET `/api/tournaments/[edition]/matches`, `/matches/[fixtureId]` and `/bracket` need no cookies. Their database queries require fixture publication and explicitly approved published revisions; direct private IDs return 404. There is no public result-write endpoint. Dynamic rendering and no-store responses keep publication withdrawal visible immediately; staff mutations also invalidate the edition layout.

Admin configures named groups and official team membership under the fixture workspace, then explicitly publishes those assignments. A team may belong to one group in an edition's Group Stage. Round-specific ranking policies require approved win/loss points, optional confirmed draw points and ordered supported criteria (points, wins, map difference, maps won). No default points, group assignment or alphabetical tiebreak is supplied. Only published group results count; knockout/cancelled fixtures are excluded. Missing or inconsistent ranking rules produce factual statistics with points/ranks pending. Equal final criteria remain tied. Group/rule changes are audited and do not rewrite source scores.
